# Database

PostgreSQL 17 is the system of record. Every value that affects an employee's pay,
entitlement, leave balance or employment status is stored here and nowhere else.

At the end of phase 0 the database exists, is hardened, and has **no application
schema**. The schema is created by Prisma migrations from phase 1.

## Connecting

| Context    | Host       | Port | Notes                                             |
| ---------- | ---------- | ---- | ------------------------------------------------- |
| Host       | `localhost`| 5435 | The default 5432 and 5433/5434 are already taken by other local stacks |
| Container  | `postgres` | 5432 | Always the service name inside the compose network |

The published port differs from the container port on purpose, so this stack can
run beside others. Applications must never hard-code either: they read
`POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER` and
`POSTGRES_PASSWORD`.

`.env.example` describes `localhost:5435` because that is correct when the
application runs on the host. `docker-compose.yml` overrides `POSTGRES_HOST` to
`postgres` and `POSTGRES_PORT` to `5432`, because inside the network the published
port does not exist. This split is the single most common cause of "connection
refused" in this project; see [DEPLOYMENT.md](DEPLOYMENT.md).

## Cluster preparation

`docker/postgres/init/01-extensions.sh` runs once, on an empty data directory.

| Extension   | Why it exists                                                                          |
| ----------- | -------------------------------------------------------------------------------------- |
| `pgcrypto`  | `gen_random_uuid()` for identifiers that must not be sequential or guessable             |
| `citext`    | Case-insensitive identifiers. Without it, `HR-001` and `hr-001` can both exist           |
| `unaccent`  | Accent-insensitive name search. Without it, searching `Jose` misses `José`, which reads to a user as missing data |

It also sets two timeouts per database:

- `statement_timeout = 30s` — a runaway report cannot hold locks open and starve
  the connection pool.
- `idle_in_transaction_session_timeout = 60s` — an abandoned transaction cannot
  pin a snapshot and block vacuum indefinitely.

**These run only on first initialisation.** To apply a change to an existing
volume, recreate it or write a migration:

```bash
npm run stack:down
docker volume rm hris_postgres-data
npm run stack:up
```

Destroying the volume deletes all data. Never do this outside local development.

## Schema conventions

Applied from the first migration onward, so they are not retrofitted later.

### Identifiers

- Primary keys are `uuid`, generated by the database (`gen_random_uuid()`).
- Identifiers are never reused and never exposed as sequential numbers, which
  would leak volume and invite enumeration.
- Public-facing references (employee codes, claim numbers) are separate, human
  readable, and unique per company — not globally unique.
- `citext` for anything a human types as an identifier.

### Money and quantities

Money is never a floating-point number. Two supported representations:

| Column type    | Use when                                                                 |
| -------------- | ------------------------------------------------------------------------ |
| `numeric(20,4)`| Amounts that must be exact: payroll, claims, ledger entries                |
| `bigint` minor units | Amounts that are whole currency units and need exact cent arithmetic  |

`numeric` is the default. Currency is stored alongside every amount; a bare
number is meaningless in a multi-company, multi-currency platform.

### Time

- `timestamptz` for every instant. A local wall-clock timestamp cannot survive a
  daylight-saving transition or a tenant in another region.
- Store the IANA timezone (`Asia/Kuala_Lumpur`) separately when the local date and
  time matter, such as an attendance shift boundary. The UTC instant alone is
  ambiguous at midnight.
- A date of birth, a leave date or a contract end date is a `date`, not a
  timestamp.

### Text and names

- Names are not unique and are never used as identifiers.
- Free text that will be searched (names, skills, locations) gets
  `pg_trgm` indexes once phase 1 introduces the first searchable table.
- Normalise for comparison in a generated column; never overwrite what the user
  typed.

### Naming

- Plural `snake_case` table names: `employees`, `leave_requests`.
- `snake_case` columns; timestamps end in `_at`, dates in `_date`, booleans read
  as assertions: `is_active`, `has_verified_email`.
- Foreign key columns are named `<singular_table>_id`.
- Every table has `created_at`, `updated_at` and `created_by_user_id`.

### Deletion

- Business records are never hard-deleted. Soft delete via `deleted_at`, filtered
  by default so a forgotten `WHERE` clause cannot destroy payroll history.
- Personal data that must disappear on request is pseudonymised, not deleted:
  audit logs keep the row and the action, and lose the identity.
- Retention periods are per record class and enforced by a scheduled job with a
  recorded decision, never by a casual `DELETE`.

## Tenant isolation

The hierarchy is Holding → Company → Entity → Division → Department → Section →
Team → Employee. Isolation is layered, deliberately:

1. **Application authorisation (primary).** Every query resolves the caller's
   permitted scope from stored state and applies it. A request never supplies its
   own scope.
2. **Row-level security (defence in depth).** Enabled per table by the migration
   that owns that schema. `SET LOCAL app.current_company_id` at the start of a
   transaction; policies filter on it.

RLS must be enabled per table. It cannot be switched on cluster-wide, and a policy
without `ENABLE ROW LEVEL SECURITY` is inert — which is the usual way RLS silently
does nothing. Every table that carries tenant data gets RLS and a test that proves
a cross-tenant read returns nothing.

Sessions use `SET LOCAL`, not `SET`. A `SET` outside a transaction leaks into the
next request that borrows the pooled connection, which is precisely how one
company's data reaches another.

## Connection pooling

Phase 1 introduces a pooler (PgBouncer in transaction mode) in front of
PostgreSQL. Until then the application uses a bounded pool sized well below
`max_connections`:

```
pool_max = (max_connections - reserved) / number_of_app_instances
```

Exceeding `max_connections` presents as intermittent "too many clients" failures
under load, not as a startup error, so the ceiling is set deliberately and
monitored.

## Migrations

Owned by Prisma from phase 1, stored in `database/migrations`, applied in order
and never edited after they have run.

Rules:

- A migration that has been applied anywhere is immutable. Correct it with a new
  migration.
- Every migration is reviewed for lock behaviour. Adding a `NOT NULL` column with a
  volatile default rewrites the table on older PostgreSQL versions; add the column,
  backfill in batches, then constrain.
- Destructive changes are two-phase: deploy code that stops using the column, then
  drop it in a later release. Never in one step.
- `database/seeds` and `database/fixtures` hold reference data and test fixtures.
  Seeds must be idempotent and must never contain real personal data.

`docker/postgres/init` prepares the cluster and creates no tables. Application
schema belongs in migrations, never in hand-written bootstrap SQL, because a
bootstrap script cannot be replayed, diffed or rolled back.

## Backup and recovery

| Property      | Target                                                              |
| ------------- | ------------------------------------------------------------------- |
| RPO           | 15 minutes                                                         |
| RTO           | 1 hour                                                             |
| Method        | Continuous archiving to object storage, plus daily base backups      |
| Retention     | Daily 35 days, weekly 12 months, monthly 7 years                     |
| Encryption    | At rest, with keys in a secret manager                               |
| Restore tests | Quarterly, into an isolated environment, timed                       |

Payroll and attendance history are business-critical and legally required to be
recoverable. A backup that has never been restored is not a backup; the quarterly
restore drill is what turns the target above into a commitment.

Point-in-time recovery is required for the primary. Restoring to a secondary and
promoting it is acceptable only if the drill proves the promotion path.

## Inspection

```bash
# Schema and extensions
docker compose exec postgres psql -U hris -d hris -c '\dt'
docker compose exec postgres psql -U hris -d hris -c '\dx'

# Current connections and their state
docker compose exec postgres psql -U hris -d hris -c \
  "SELECT state, count(*) FROM pg_stat_activity GROUP BY state;"

# Long-running queries, which the statement timeout should normally prevent
docker compose exec postgres psql -U hris -d hris -c \
  "SELECT pid, now() - query_start AS age, left(query, 80)
   FROM pg_stat_activity
   WHERE state <> 'idle' AND now() - query_start > interval '5 seconds'
   ORDER BY age DESC;"
```
